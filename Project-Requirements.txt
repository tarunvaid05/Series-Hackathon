Project Requirements: Series Events Messaging System (SEMS)
Hackathon Build – Phase 1 & 2
version: 2025-12-06

1 Overview
The Series Events Messaging System (SEMS) enables the creation of real-world events through natural language messaging. Users communicate with a designated Series-issued phone number via SMS or iMessage to initiate and complete an event creation workflow.

In Phase 1, SEMS supports basic conversational event creation only. Phase 2 extends this with event editing, event discovery, joining events, leaving events, and deleting events. Events are persisted to local JSON storage. The goal is to validate conversational UX, message routing, and interaction flow using the provided messaging API and Kafka connectivity.

2 User Management
Phase 1 supports a single user role: end user identified solely by phone number. The system actor is the Series Events Number, representing backend processing exposed as a messaging participant.

No account creation, authentication, or user roles beyond the end user are required.

2.1 Message-based Interaction
Users initiate interaction by sending free-form text to the Series Events Number. The system responds sequentially to collect required event information using scripted prompts. Interaction occurs entirely through messaging.

3 Event Creation Workflow
SEMS enables conversational event creation. When a user expresses intent to create an event, SEMS runs a guided interaction to collect the following:

Event title
Event description
Event date/time (free-form text accepted)
Event location
Optional participant capacity

The system summarizes collected information and asks for confirmation. Phase 1 does not require temporal parsing, geocoding, or data validation. The event may be logged or printed but persistence is not required.

3.1 Intent triggering
A workflow begins when SEMS detects keywords indicating event creation, such as “create event” or “I want to host an event”. Keyword matching is sufficient; natural language understanding is not required for Phase 1.

3.2 Messaging behavior
SEMS maintains conversational state per user phone number until completion or cancellation. After confirmation, SEMS clears state. Timeouts and abandoned conversations may be reset at system discretion.

4 Event Structure
Phase 1 maintains transient in-memory event objects for conversational flow. A minimal data model is sufficient:

User phone number
Title
Description
Raw date/time text
Location
Participant limit (nullable)

No parsing or validation features are required. Editing and deletion are Phase 2 features.

5 System Behaviors
SEMS must:
Detect creation intent
Prompt sequentially for information
Maintain conversational state
Provide a summary and request confirmation
Accept “confirm” or “restart”
Clear state after completion

If a user sends “cancel” at any point, SEMS terminates the interaction and returns to idle.

Unexpected or malformed replies should be tolerated; SEMS may accept neutral input and continue.

6 Messaging API Integration
The Series messaging API delivers inbound messages to SEMS and sends system responses back to users.

Phase 1 must support:
Receiving inbound message payloads
Extracting phone number and message body
Sending outbound messages via the API
Maintaining transient conversational state

Kafka logging of completed events is optional.

7 Non-Goals (Phase 1 & 2 Limits)
SEMS does not include databases (uses local JSON file), identity authentication, group chats, reminders, agentic routing, recommendation logic, or any UI besides messaging.

8 Usability Requirements
SEMS must guide users conversationally. Prompts should be simple, confirmation messages should acknowledge input, and invalid input must not break progression.

9 Current Date and Timing
Phase 1 does not parse or validate dates; user-provided text is accepted as-is.

10 Deployment
Users interact solely via SMS/iMessage through the Series Events number. No installations, accounts, or web interfaces are required. SEMS may run locally or remotely as long as it interfaces with the messaging API.

--- PHASE 2 REQUIREMENTS ---

11 Data Persistence
Phase 2 uses a local JSON file for event storage at data/events.json.

11.1 Event Data Structure
Each event contains:
- id: unique identifier (UUID)
- host_phone: phone number of creator
- title: event title
- description: event description
- datetime: raw date/time text
- location: event location
- capacity: participant limit (nullable for unlimited)
- participants: list of phone numbers who joined

11.2 Storage Behavior
Events are persisted on creation confirmation. Updates are saved immediately on edit confirmation. File is read on startup and written on each modification.

12 Event Editing Workflow
Only the host (creator) can edit their own events.

12.1 Edit Intent Triggering
Workflow begins when SEMS detects keywords like "edit event", "edit my event", "change my event", or "modify event".

12.2 Edit Flow
1. SEMS lists events hosted by the user with numbers
2. User selects event by number
3. SEMS presents field menu:
   "Which field would you like to change?
   1. Title
   2. Description
   3. Date/Time
   4. Location
   5. Capacity
   Reply with a number or 'done' to finish editing."
4. User selects field number
5. SEMS prompts for new value
6. User provides new value
7. SEMS confirms change and returns to field menu
8. Loop continues until user says "done"
9. SEMS shows updated summary and clears edit state

12.3 Edit Restrictions
Users can only edit events they created (host_phone matches). If user has no events, inform them.

13 Event Discovery and Joining Workflow

13.1 Discovery Intent Triggering
Workflow begins when SEMS detects keywords like "find events", "what's happening", "events near", "join event", "any events", or location-based queries.

13.2 Discovery Flow
1. SEMS shows available events (excluding user's own events and full-capacity events)
2. Events display: title, date/time, location, spots remaining
3. User can reply with event number to join
4. SEMS confirms join and updates participant list
5. Capacity display updates (e.g., "3/10 spots filled")

13.3 Join Restrictions
- Users cannot join their own events
- Users cannot join events at full capacity
- Users cannot join events they already joined

14 Leave Event Workflow

14.1 Leave Intent Triggering
Workflow begins when SEMS detects keywords like "leave event", "cancel rsvp", "drop out", or "quit event".

14.2 Leave Flow
1. SEMS lists events the user has joined
2. User selects event by number
3. SEMS confirms removal and updates participant list
4. Capacity is restored

14.3 Leave Restrictions
Users can only leave events they have joined. Hosts cannot "leave" their own events (must delete instead).

15 Delete Event Workflow

15.1 Delete Intent Triggering
Workflow begins when SEMS detects keywords like "delete event", "remove event", "cancel event" (when host), or "delete my event".

15.2 Delete Flow
1. SEMS lists events hosted by the user
2. User selects event by number
3. SEMS asks for confirmation: "Are you sure you want to delete '[title]'? Reply 'yes' to confirm."
4. On confirmation, event is removed from storage
5. SEMS confirms deletion

15.3 Delete Restrictions
Only hosts can delete their own events. Participants are implicitly removed when event is deleted.

16 User Experience Guidelines

16.1 Pretty Printing
- Use clear formatting with line breaks for readability
- Number lists for selection (1, 2, 3...)
- Show relevant details concisely
- Acknowledge each user action

16.2 Event Display Format
For event listings:
"[number]. [title]
   When: [datetime]
   Where: [location]
   Spots: [current]/[capacity] or 'unlimited'"

16.3 Error Handling
- Invalid number selections: prompt to try again
- No events found: friendly message with suggestion
- Already joined: inform user they're already participating
- At capacity: inform user event is full

--- PHASE 3 REQUIREMENTS ---

17 User Registration
Users must provide their name before creating or joining events.

17.1 Name Collection
- First-time users are prompted: "What's your name?"
- Name is stored in data/users.json with phone number as key
- Name persists across all interactions
- Existing users skip this step

17.2 User Data Structure
```
{
  "+1234567890": {"name": "John", "registered_at": "2025-12-06T..."}
}
```

18 Join Request Flow
Joining events now requires host approval.

18.1 Request Flow
1. User texts "join event" or similar intent
2. SEMS shows available events (open status, not full, not own)
3. User selects event by number
4. SEMS sends request notification to host: "[Name] is requesting to join [Event]. Reply 'approve [name]' or 'deny [name]'"
5. User receives: "Request sent! Waiting for host approval."

18.2 Approval Flow
- Host replies "approve [name]" → participant added, both notified
- Host replies "deny [name]" → request denied, requester notified, cannot re-apply

18.3 Request Data Structure
Events track pending and denied requests:
```
{
  "pending_requests": ["+1111111111"],
  "denied_requests": ["+2222222222"]
}
```

19 Close Event Flow
Hosts can close events to stop accepting new participants.

19.1 Close Intent Triggering
Keywords: "close event", "close registration", "stop registration"

19.2 Close Flow
1. SEMS lists host's open events
2. Host selects event by number
3. SEMS asks: "Would you like to create a group chat with all participants? (yes/no)"
4. If yes: create group chat via messaging API, send welcome message
5. Event status set to "closed", hidden from discovery

19.3 Event Status
- "open": visible in discovery, accepts requests
- "closed": hidden from discovery, no new requests

20 Group Chat Creation

20.1 Group Chat via Messaging API
Use POST /api/chats with multiple phone_numbers to create group chat.

20.2 Welcome Message Format
```
Welcome to [Event Name]!

When: [datetime]
Where: [location]

Attendees:
- [Host Name] (Host)
- [Participant 1 Name]
- [Participant 2 Name]
...

See you there!
```

20.3 Group Chat Behavior
- SEMS sends only the welcome message
- No further SEMS bot interaction in group chat
- Participants coordinate directly in group

21 Updated Capacity Prompt
When collecting capacity, prompt clarifies: "How many people can attend? (not including yourself, or 'skip' for no limit)"

22 View Attendees Feature

22.1 SEMS Messaging Command
Users can view attendees for their hosted events via messaging.

22.1.1 View Attendees Intent Triggering
Keywords: "view attendees", "who's coming", "show attendees", "list attendees", "who joined"

22.1.2 View Attendees Flow
1. SEMS lists events hosted by the user
2. User selects event by number
3. SEMS displays confirmed participants with name and phone:
   "Attendees for [Event Title]:
   - John (+1234567890)
   - Sarah (+0987654321)
   Total: 2 attending"
4. If no attendees: "No one has joined [Event Title] yet."

22.2 Dashboard Attendee Display
The web dashboard shows attendees in the "My Events" tab.

22.2.1 Inline Expansion
- Each event in My Events has an expandable section
- Click to expand/collapse attendee list
- Shows confirmed participants with name and phone number
- Format: "Name (+phone)" for each attendee

22.2.2 Pending Request Management
- Dashboard displays pending join requests for each event
- Host can approve or deny requests via dashboard buttons
- Approve: adds user to participants, notifies both parties
- Deny: adds user to denied list, notifies requester

22.3 API Endpoints

22.3.1 Approve Request
POST /api/events/[id]/approve
Body: { "phone": "+1234567890" }
- Moves phone from pending_requests to participants
- Returns updated event

22.3.2 Deny Request
POST /api/events/[id]/deny
Body: { "phone": "+1234567890" }
- Moves phone from pending_requests to denied_requests
- Returns updated event

22.3.3 Bulk User Lookup
POST /api/users/lookup
Body: { "phones": ["+1234567890", "+0987654321"] }
- Returns mapping of phone numbers to user names
- Format: { "+1234567890": { "name": "John" }, ... }
